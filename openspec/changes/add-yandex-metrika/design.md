# Design

## Context

См. proposal.md — Why. В src/app/layout.tsx общий серверный layout содержит html/body и содержимое страницы; аналитики сейчас нет. Next.js настроен на output: export. ContactSection получает публичную конфигурацию контактов отдельно, PDF открывается в новой вкладке. В tests/site.spec.ts уже есть Playwright-проверки ссылок, клавиатуры, отключённого JavaScript и адаптивности. В deploy/nginx.conf и gateway-конфигурациях CSP не обнаружена.

Создание design необходимо из-за подключения внешнего сервиса и требований к загрузке и повторной инициализации.

## Goals / Non-Goals

**Goals:** сохранить статическую сборку и изолировать загрузку аналитики от работы интерфейса; дать воспроизводимые проверки без реального трафика в счётчик из CI.

**Non-Goals:** вводить серверный процесс, дополнительную npm-библиотеку, маршрутизацию для несуществующих страниц или передачу пользовательских идентификаторов. Полный объём указан в proposal.md.

## Decisions

1. Подключить предоставленный bootstrap через next/script со стабильным id и стратегией afterInteractive в общем layout; при необходимости вынести разметку в небольшой компонент. Это использует имеющийся механизм Next.js и не блокирует первый показ страницы. Альтернативы: beforeInteractive раньше запускает аналитику, но помещает её в критический путь; useEffect усложняет защиту от повторной инициализации в Strict Mode. Bootstrap не привязывать к состоянию карусели или загрузке контактов. При проектировании защиты учитывать и повторный init, и повторную вставку внешнего script: проверка document.scripts в исходном коде защищает только загрузчик.
2. Сохранить URL https://mc.yandex.ru/metrika/tag.js?id=114281247 и все значения init из запроса, включая ssr, ecommerce:"dataLayer", текущие referrer и location.href. Идентификатор публичный, его не нужно добавлять в секреты или runtime JSON. Создание собственных ecommerce-событий не требуется. Альтернатива с переменными окружения добавляет конфигурацию без согласованного сценария нескольких счётчиков.
3. Вывести noscript непосредственно в серверной разметке body; адаптировать style в JSX, сохранить position:absolute и left:-9999px, пустой alt. Это обеспечивает наличие пикселя в out/index.html. Альтернатива с созданием через эффект не работает без JavaScript.
4. Автоматические проверки перехватывают внешние запросы: заглушка tag.js фиксирует очередь init и параметры, отдельный сценарий блокирует сервис. Для отключённого JavaScript проверять HTML и запрос watch. Существующие smoke-тесты также изолировать от реальной Метрики. Реальное поступление визита и запись Вебвизора проверяются вручную после публикации.
5. Использовать текущие Next.js/React/TypeScript, nginx и Playwright. Новые backend и npm-зависимости не нужны; локальные задачи укладываются в интервалы до двух часов и поддерживают исходный бюджет MVP 48 часов. Время обработки записей Яндексом и доступ к кабинету в оценку автоматических проверок не входят.
6. Подключение действует во всех сборках; отдельного переключателя окружений в запросе нет. Для ручного просмотра локально учитывать возможные тестовые визиты, а CI изолировать перехватом сетевых запросов. Ограничение принимаемых адресов можно проверить в кабинете счётчика, не вводя новый механизм конфигурации сайта.

## Risks / Trade-offs

- Блокировщики и недоступность сервиса → интерфейс не зависит от ответа Метрики; полноту статистики гарантировать нельзя.
- Вебвизор выключен в кабинете → перед приёмкой проверить обе настройки по [инструкции Яндекса](https://www.yandex.com/support/metrica/ru/webvisor/settings); webvisor:true в коде недостаточно для подтверждения записи.
- Запоздалый запуск после интерактивности → самые ранние действия могут не попасть в запись; такой компромисс сохраняет быстрый показ резюме.
- Внешний PDF → отслеживается взаимодействие со страницей и стандартная аналитика ссылок; чтение документа на другом сайте не наблюдается.
- Повторная инициализация → стабильный script id и проверка одной команды init при повторном рендере.

## Migration Plan

1. Реализовать подключение, проверки и инструкцию в отдельном worktree от origin/feat/yandex-metric-integration-24.
2. Пройти локальные проверки и собрать статический out; проверить присутствие noscript и отсутствие зависимости от серверного Node.js.
3. Опубликовать через существующий процесс production после отдельного запроса на доставку. В кабинете 114281247 сверить адрес сайта и настройки Вебвизора, затем выполнить контрольный визит без блокировщика.
4. Подтвердить поступление визита и запись после обработки Яндексом по [инструкции проверки счётчика](https://yandex.ru/support/metrica/ru/general/check-counter.html?lang=ru). Если кабинет недоступен, явно оставить эту проверку незавершённой.
5. Откатить публикацию на предыдущий релиз существующим механизмом; накопленная статистика остаётся в кабинете. Миграция данных не требуется.
