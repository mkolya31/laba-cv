# Spec Delta

## Purpose

Обеспечить воспроизводимую проверку и публикацию сайта dev.kolyach.me через существующий gateway Ubuntu VPS, чтобы автор мог безопасно обновлять сайт без нарушения работы соседних проектов.

## ADDED Requirements

### Requirement: Воспроизводимая проверенная сборка

Проект SHALL предоставлять документированные команды чистой установки зависимостей, lint, проверки форматирования, типов и production-сборки. Сборка SHALL формировать полный набор статических файлов страницы и локальных ресурсов, пригодный для раздачи веб-сервером без Python-бэкенда.

#### Scenario: Чистое окружение

- **WHEN** в поддерживаемой документированной среде выполняются установка по lock-файлу и команды проверок
- **THEN** проверки завершаются успешно и создаётся набор файлов страницы с портретом и загрузкой `resumeUrl` из runtime-конфигурации; реальный PDF и серверное окружение не требуются для сборки и не включаются в её артефакт

### Requirement: Проверка изменений до публикации

Для открытых pull request, обновлений веток `main` и `develop`, а также после merge pull request в `production` автоматизация SHALL выполнять lint, проверку форматирования, типов, пользовательские smoke-проверки и production-сборку. После merge SHALL проверяться итоговый коммит слияния. Неуспешные проверки SHALL исключать публикацию соответствующего изменения.

#### Scenario: Ошибка проверки

- **WHEN** хотя бы одна обязательная проверка завершается ошибкой
- **THEN** изменение не публикуется и действующая версия сайта сохраняется

### Requirement: Автоматическая доставка

После успешных проверок GitHub Actions SHALL автоматически публиковать на выбранном VPS артефакт проверенного итогового коммита PR в `production`. Источником SHALL быть только `develop`, `release/*` или `hotfix/*` с непустым именем после `/`. Push в `production` SHALL запускать проверки; деплой SHALL требовать подтверждения через GitHub API, что точный SHA — итог слитого PR из разрешённой ветки.

#### Scenario: Успешное обновление

- **WHEN** PR из `develop`, `release/1.0` или `hotfix/fix` слит в `production` и итоговый коммит прошёл обязательные проверки
- **THEN** новая сборка публикуется без ручного копирования файлов и сайт показывает новую редакцию

#### Scenario: Запрещённая исходная ветка

- **WHEN** PR в `production` открыт из `main`, `feature/example` или другой ветки вне разрешённого набора
- **THEN** обязательная проверка `production-source` завершается ошибкой, merge блокируется защитой ветки и деплой не выполняется

#### Scenario: Событие без публикации

- **WHEN** PR закрыт без merge, слит в другую ветку либо выполнен прямой push
- **THEN** деплой не запускается и действующая версия сайта сохраняется

### Requirement: Безопасная доставка

Доступ к серверу SHALL задаваться секретами окружения доставки, не содержаться в публичных файлах и применяться только к выделенному сайту. Учётная запись CI SHALL работать без sudo и Docker, не читать исходный серверный env и не изменять gateway, TLS, tools, среду Node.js, постоянные контакты и PDF. Параллельные доставки SHALL не смешивать релизы.

#### Scenario: Ошибка передачи

- **WHEN** передача сборки на сервер завершается неуспешно
- **THEN** посетителю продолжает отдаваться предыдущая полная версия, без частично обновлённой страницы

#### Scenario: Ограниченный доступ CI

- **WHEN** доставка выполняется под отдельной учётной записью CI
- **THEN** доступны запись новых релизов, их хешированных ресурсов и переключение текущей версии, а изменение соседних проектов, gateway, TLS, tools, окружения, постоянных контактов и PDF запрещено
- **AND** публичная конфигурация и выбранный локальный PDF доступны для чтения при preflight

### Requirement: Совместимость с существующим gateway

Сайт SHALL обслуживаться отдельным контейнером через существующий gateway и общую сеть `web`, без новых публичных портов. HTTPS, перенаправление HTTP и ACME SHALL обслуживаться общим gateway. Добавление сайта SHALL не требовать пересоздания gateway или изменения маршрутов соседних проектов.

#### Scenario: Подключение сайта

- **WHEN** активированы контейнер сайта и новый virtual host dev.kolyach.me
- **THEN** сайт доступен через существующие порты 80/443, внутренний контейнер не публикует порты хоста и состояние соседних сайтов сохраняется относительно исходной проверки

#### Scenario: Пересоздание контейнера сайта

- **WHEN** внутренний контейнер пересоздан и получил другой IP в сети `web`
- **THEN** gateway снова маршрутизирует запросы по сетевому имени без изменения конфигурации или reload gateway

### Requirement: Серверная среда без сборки приложения

Production-сборка SHALL выполняться в CI. Серверные скрипты SHALL запускаться на отдельно установленной администратором Node.js 24 без установки npm-зависимостей проекта на VPS. Статическая раздача SHALL не требовать постоянно работающего процесса Node.js.

#### Scenario: Доставка готового артефакта

- **WHEN** CI передаёт проверенный статический артефакт на VPS
- **THEN** сервер валидирует и активирует его без сборки приложения, а сайт продолжает раздаваться после завершения серверного скрипта

### Requirement: Проверка релиза до переключения

Перед активацией релиза SHALL проверяться HTML, портрет, ресурсы сборки, runtime-конфигурация и выбранный PDF. Файлы SHALL быть доступны для чтения из контейнера с его фактическими правами. Неуспешный preflight SHALL сохранять прежний текущий релиз.

#### Scenario: Неполный или нечитаемый релиз

- **WHEN** обязательный ресурс отсутствует, конфигурация или PDF некорректны либо файл недоступен контейнеру
- **THEN** активация завершается ошибкой до переключения и прежняя версия остаётся доступной

### Requirement: Сериализация публикации и отката

Активация и откат SHALL использовать общую серверную блокировку. Запоздавший запуск автоматического деплоя SHALL не заменять более новый успешно опубликованный запуск. Явный документированный откат SHALL оставаться возможным и SHALL не разрешать последующую публикацию устаревшего запуска CI.

#### Scenario: Конкурирующие операции

- **WHEN** одновременно запрошены активация и откат
- **THEN** операции выполняются последовательно, проверка результата и возможный возврат не смешиваются с другой публикацией

#### Scenario: Запоздавший запуск CI

- **GIVEN** уже успешно опубликован более новый запуск CI
- **WHEN** старый запуск доходит до активации, в том числе после ручного отката
- **THEN** он отклоняется без изменения текущей версии

### Requirement: Защита production

Ветка `production` SHALL принимать изменения только через pull request с успешными обязательными checks `production-source` и `verify`. Защита SHALL требовать актуальности PR относительно целевой ветки, запрещать прямой push, force push и удаление ветки, применяться к администраторам без обходов. Workflow SHALL повторно проверять исходную ветку перед деплоем независимо от настройки защиты.

#### Scenario: Попытка обхода PR

- **WHEN** пользователь пытается напрямую обновить ветку `production` или слить PR с ошибкой обязательного check
- **THEN** GitHub отклоняет обновление защищённой ветки

### Requirement: Публичный HTTPS-адрес

Сайт SHALL открываться по HTTPS на dev.kolyach.me без регистрации. Запрос HTTP SHALL перенаправляться на HTTPS, кроме ACME challenge. Главная страница, изображения, стили, скрипты и резюме SHALL открываться без ошибок и смешанного содержимого. Сертификат SHALL обслуживаться существующим механизмом продления gateway.

#### Scenario: Проверка внешнего адреса

- **WHEN** посетитель открывает подтверждённый домен по HTTP
- **THEN** он перенаправляется на HTTPS с действительным сертификатом и получает читаемую страницу с рабочими ресурсами и PDF

#### Scenario: ACME и продление

- **WHEN** выполняется проверка владения доменом или плановое продление сертификата dev.kolyach.me
- **THEN** challenge доступен по HTTP, сертификат обновляется существующим Certbot и применяется после успешной проверки конфигурации без остановки gateway

### Requirement: Обновление и откат релиза

Процесс публикации SHALL позволять восстановить предыдущий рабочий релиз страницы и её ресурсов. При локальном варианте PDF SHALL храниться независимо от релизов: деплой, откат и очистка SHALL не изменять текущий документ. Внешний `resumeUrl` SHALL не требовать локального файла. После обновления страницы повторное открытие SHALL получать её актуальную редакцию с учётом повторной проверки кеша.

#### Scenario: Проверка отката

- **GIVEN** опубликовано минимум два релиза сайта, а PDF затем заменён независимо
- **WHEN** выполняется документированный откат
- **THEN** главная страница и её ресурсы возвращаются к предыдущей версии, а PDF остаётся в последней загруженной редакции

#### Scenario: Сохранность при деплое и очистке

- **GIVEN** автор заменил PDF непосредственно на сервере
- **WHEN** публикуется новый релиз сайта и удаляются старые каталоги релизов
- **THEN** файл PDF и его содержимое сохраняются без изменений, документ доступен по `/resume.pdf`

#### Scenario: Переключение при работающем контейнере

- **WHEN** активируется другой релиз или выполняется откат
- **THEN** следующий запрос HTML получает выбранную версию без перезапуска контейнера сайта или reload gateway

### Requirement: Проверка опубликованной версии

После переключения SHALL проверяться HTTPS-страница выбранного релиза и её ресурсы. Неуспешная проверка SHALL приводить к восстановлению предыдущего релиза и ошибке деплоя. При первой публикации без предшественника SHALL применяться документированное отключение только нового virtual host.

#### Scenario: Ошибка после переключения

- **GIVEN** имеется предыдущий рабочий релиз
- **WHEN** проверка новой опубликованной версии завершается ошибкой
- **THEN** предыдущий указатель восстанавливается, деплой отмечается неуспешным, постоянные конфигурация и PDF сохраняются

#### Scenario: Ошибка первой публикации

- **GIVEN** предыдущего рабочего релиза нет
- **WHEN** первая публичная проверка завершается ошибкой
- **THEN** процедура возврата отключает только новый virtual host, не затрагивая соседние сайты и постоянные файлы

### Requirement: Доступность ресурсов старых страниц

Хешированные ресурсы ранее опубликованных страниц SHALL оставаться доступными после переключения и отката независимо от текущего релиза. Путь существующего хешированного ресурса SHALL не перезаписываться другим содержимым. Очистка SHALL учитывать сохраняемые релизы и политику кеширования.

#### Scenario: Запрос старого JS после деплоя

- **GIVEN** посетитель открыл страницу до публикации нового релиза
- **WHEN** после переключения страница запрашивает свой ранее опубликованный JS или CSS
- **THEN** ресурс доступен по прежнему URL с прежним содержимым

#### Scenario: Коллизия ресурса

- **WHEN** новый релиз содержит другое содержимое по уже существующему хешированному пути
- **THEN** публикация отклоняется без перезаписи ресурса и переключения релиза

### Requirement: Ограниченная очистка релизов

Процедура очистки SHALL сохранять последние пять успешных релизов, текущий релиз и необходимые им ресурсы. Очистка SHALL ограничиваться проверенными каталогами этого сайта, сохранять shared, tools и окружение и SHALL не выполнять глобальную очистку Docker.

#### Scenario: Очистка после нескольких публикаций

- **GIVEN** успешно опубликовано больше пяти релизов
- **WHEN** выполняется документированная очистка
- **THEN** последние пять успешных и текущий релиз доступны для использования, постоянные файлы и соседние проекты не изменены, ресурсы старых страниц сохраняются согласно отдельной политике

### Requirement: Независимая конфигурация контактов

Сборка и CI SHALL работать без реальных серверных переменных. На VPS скрипт SHALL формировать публичный JSON только из телефона, Telegram и `RESUME_URL`, проверять значения и заменять файл целиком. Пустой или отсутствующий `RESUME_URL` SHALL давать `/resume.pdf`; явно заданный некорректный адрес SHALL приводить к ошибке без замены прежнего JSON. Деплой, откат и очистка SHALL сохранять окружение и конфигурацию.

#### Scenario: Обновление без сборки

- **WHEN** автор меняет контактные переменные либо `RESUME_URL` на VPS и повторно запускает генерацию
- **THEN** новый JSON доступен по прежнему адресу, без запуска сборки или передачи значений в CI

#### Scenario: Неверное значение переменной

- **GIVEN** имеется действительная публичная конфигурация
- **WHEN** генерация получает отсутствующую обязательную контактную переменную или явно заданное некорректное значение
- **THEN** скрипт сообщает об ошибке без вывода реальных значений и не заменяет действительный файл

#### Scenario: Сохранность при публикации и откате

- **GIVEN** автор независимо обновил конфигурацию контактов
- **WHEN** выполняются публикация, очистка старых релизов или откат сайта
- **THEN** окружение и последняя конфигурация контактов сохраняются, остальные переменные окружения не появляются в публичном JSON

#### Scenario: Недопустимая ссылка резюме

- **GIVEN** существует действительная runtime-конфигурация
- **WHEN** генератор получает явно заданный `RESUME_URL`, отличный от `/resume.pdf` и абсолютного HTTPS-адреса
- **THEN** генерация завершается ошибкой, прежний JSON сохраняется и небезопасная ссылка не публикуется

#### Scenario: Атомарная замена внутри контейнера

- **GIVEN** контейнер сайта уже запущен
- **WHEN** автор атомарно заменяет публичный JSON или локальный PDF на хосте
- **THEN** следующий запрос получает новую редакцию без перезапуска контейнера и reload gateway, а env и tools недоступны по HTTP и не смонтированы в контейнер сайта

### Requirement: Проверка готовности публичной версии

Первый релиз SHALL проходить проверку внешнего URL, мобильной компоновки, клавиатурной навигации, переключателя, ссылок, PDF и текста кейсов. Ввод сайта SHALL сохранять доступность других сайтов того же VPS.

#### Scenario: Приёмка

- **WHEN** завершена первая публикация
- **THEN** зафиксированы результаты проверки ширин 360, 768 и 1440 CSS-пикселей, увеличения текста до 200%, клавиатуры, ссылок и PDF, а также доступности соседних сайтов VPS

#### Scenario: Сравнение с исходным состоянием VPS

- **GIVEN** до интеграции зафиксированы HTTPS 200 у kolyach.me, wedding.kolyach.me и kamoved.ru и существующий 502 у 2popuga.kolyach.me
- **WHEN** завершены добавление сайта и проверка отката
- **THEN** ранее работавшие сайты доступны, существующий сбой учтён отдельно и не маскирует новые регрессии
