# Design

## Context

Мотивация и объём описаны в `proposal.md`. Приложение Next.js со статическим экспортом, локальные проверки и базовый workflow уже реализованы. Изменение находится в apply; действующих main specs пока нет. Пользователь выбрал Next.js, Ubuntu VPS, nginx и GitHub Actions; Python отложен до отдельной итерации.

Архитектура VPS обследована 15 ноября 2026 года; [предложение интеграции](../../../docs/vps-integration-proposal.md) согласовано автором. Ubuntu 24.04, около 2 ГиБ RAM и 6,2 ГиБ свободного диска на момент обследования. Общий контейнер `web-gateway-nginx` занимает 80/443 и соединён с frontend-контейнерами сетью `web`. Certbot и ежедневный cron обслуживают TLS. DNS dev.kolyach.me уже указывает на VPS, но virtual host и сертификат отсутствуют. Node.js на VPS не найден. Это подтверждённый контекст, а не результат выполненного деплоя.

Тексты кейсов получены в обсуждении; портрет включён в приложение, документ резюме получен отдельно и не добавлен в git. Предварительный макет передан изображением: крупная фотография слева, заголовок справа, тёмная основа, диагонали и декоративное окно кода. Макет задаёт направление, но не содержит блока кейсов и мобильной композиции. Публичную доступность исходников и реальные серверные контакты ещё требуется проверить.

## Goals / Non-Goals

**Goals:**

- Собрать первый пригодный для отправки релиз в пределах 48 часов разработки; получение материалов и доступа к серверу может влиять на календарную дату публикации.
- Сохранить возможность менять тексты и контакты без переработки компонентов, а PDF — непосредственно на сервере без пересборки и деплоя сайта.
- Оставить на сервере простую статическую публикацию и сохранить читаемый контент при недоступности клиентского JavaScript.
- Вписать сайт в существующий gateway без новых публичных портов и ухудшения доступности соседних проектов; сохранять безопасное переключение и откат при работающем контейнере.

**Non-Goals:**

- Проектировать будущий Python API до появления полезного сценария.
- Создавать универсальную систему портфолио, редактор контента или инфраструктуру для других сайтов kolyach.me.
- Копировать растровый макет целиком как интерфейс; тексты, ссылки и кнопки должны быть настоящими элементами страницы.

## Decisions

### Статическая сборка Next.js

Предлагаем App Router, TypeScript и `output: 'export'`: сборка формирует каталог `out`, который отдаёт nginx. Интерактивность сосредоточена в небольшом клиентском компоненте смены фраз. Остальной контент формируется при сборке. Источник: [официальная документация Next.js](https://nextjs.org/docs/app/guides/static-exports).

Версии Next.js и React зафиксированы lock-файлом; среда сборки — Node.js 24 по `.nvmrc` и `package.json`. Используем имеющиеся npm и конфигурацию `@kolyach/eslint-config`, уже созданную командой `npx @kolyach/eslint-config init`; повторная инициализация не является отдельной задачей. Ограничение в 48 часов поддерживается статическим экспортом, сборкой в CI, повторным использованием gateway и существующих JS-валидаторов без разработки API или второй реализации на другом языке.

Альтернативы: постоянный процесс Next.js потребовал бы сопровождения сервиса без полезных серверных функций; Python для раздачи HTML добавил бы аналогичную нагрузку. Чистый HTML мог бы решить задачу, но не соответствует выбранному пользователем Next.js.

### Структура и данные

Одна главная страница: знакомство → четыре кейса → резюме и контакты → рассказ о создании сайта и исходники. В первом экране нет ссылки, позволяющей перейти к резюме до кейсов. Визуальный порядок, порядок DOM и клавиатурного обхода согласованы; прокрутка и доступ к ссылкам не блокируются искусственно.

Реализованное размещение: `src/app/` для страницы и метаданных, `src/components/` для блоков, `src/content/` для типизированных данных, `public/` для портрета и других ресурсов сборки. PDF хранится отдельно на сервере и не включается в `public/`, `out`, git или артефакт доставки. Снимки проектов необязательны для первого релиза. Декор выполняется преимущественно CSS; библиотека анимаций и внешний UI-kit не нужны для простого переключения.

### Контакты и ссылка на резюме из окружения сервера

Телефон и Telegram задаются на VPS через `CONTACT_PHONE` и `CONTACT_TELEGRAM_URL`. Реальные значения не хранятся в исходниках, git, тестовых данных, логах CI или артефакте сборки. В репозитории документируются только имена переменных и фиктивные примеры. Файл окружения, если он используется, размещается вне публично раздаваемых каталогов.

Дополнительная переменная `RESUME_URL` задаёт адрес PDF-резюме. Если она отсутствует или пуста, используется `/resume.pdf`; также допустим абсолютный HTTPS-адрес. Явно заданный некорректный адрес не заменяется молча значением по умолчанию: генератор сообщает об ошибке и сохраняет прежнюю конфигурацию. При внешнем адресе локальный PDF не требуется для публикации; проверяется доступность документа без авторизации по выбранной ссылке. Условия кеширования внешнего сервиса не контролируются нашим nginx.

Поскольку сайт экспортируется статически, серверные переменные нельзя читать через клиентский `process.env`: значения `NEXT_PUBLIC_*` фиксируются при сборке. Основание: [документация Next.js](https://nextjs.org/docs/app/guides/environment-variables#bundling-environment-variables-for-the-browser). Вместо этого отдельный скрипт на VPS читает только три перечисленные переменные, проверяет телефон и URL, сериализует поля `phone`, `telegramUrl` и `resumeUrl` в JSON и атомарно заменяет файл в постоянном каталоге вне релизов. Весь набор переменных окружения никогда не экспортируется.

nginx отдаёт этот файл по `/runtime-config.json` с типом `application/json` и политикой `Cache-Control: no-store`; кеш открытых файлов для этого адреса отключён. Браузер загружает конфигурацию при открытии страницы, проверяет значения и формирует `tel:`, ссылку Telegram и ссылку резюме. В публичном JSON находятся только предназначенные посетителям поля. Постоянно работающий API или Python-сервис не нужен.

До загрузки, при ошибке сети или неверной конфигурации ссылки резюме и контактов не активируются и не подменяются фиктивными адресами. Посетителю доступно краткое сообщение об их недоступности; детали серверной настройки в интерфейс не выводятся. Без JavaScript показывается сообщение о необходимости JavaScript для контактов и резюме; имя, кейсы и ссылки на исходники и SberUnity доступны как обычный HTML.

Для обновления контактов или ссылки резюме автор меняет окружение и повторно запускает скрипт генерации, без пересборки сайта. Если проверка или генерация завершается ошибкой, прежний JSON сохраняется. Деплой, откат и очистка релизов не заменяют и не удаляют файл окружения и текущую конфигурацию. CI использует только фиктивную конфигурацию для проверки обоих вариантов резюме, успешной загрузки и обработки ошибок; настоящая конфигурация проверяется на VPS перед публикацией.

### Независимое обновление PDF

Ссылка «моё резюме» использует `resumeUrl` из runtime-конфигурации и открывает документ в новой вкладке через `target="_blank"` с `rel="noopener"`. Исходная вкладка сохраняет страницу сайта и положение прокрутки. Ссылка не инициирует принудительное скачивание. Описанные ниже хранение, замена и кеширование локального PDF применяются только при `resumeUrl = /resume.pdf`; внешний вариант не требует файла на VPS.

Локальное резюме доступно по постоянному адресу `/resume.pdf`. Внутренний nginx сопоставляет этот адрес с `/srv/kolyach-dev/shared/resume.pdf`, независимо от указателя текущего релиза. Способ сопоставления описан в [документации nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#alias).

Автор загружает подготовленный PDF через SSH/SFTP под временным именем в том же каталоге, проверяет файл и права чтения nginx, затем атомарно переименовывает его в `resume.pdf`. До успешной замены доступна предыдущая целая редакция; после замены новые запросы получают новую. Пересборка, коммит, GitHub Actions и перезапуск или перезагрузка nginx для обычной замены файла не нужны. Веб-интерфейс загрузки не создаётся.

Для этого адреса задаётся `Content-Type: application/pdf` и политика `Cache-Control: no-store`; отключаются унаследованный кеш открытых файлов и условные ответы, способные вернуть старую редакцию при совпадении размера и времени изменения. Проверяется повторный запрос по тому же URL после замены, в том числе при одинаковом размере файлов. Заголовки настраиваются средствами [nginx](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header). Уже открытая вкладка PDF сама не обновляется: гарантия относится к следующему открытию/запросу.

Сборка и CI не требуют наличия реального резюме. Smoke-проверки используют фиктивные `/resume.pdf` и внешний HTTPS-адрес, проверяют открытие в новой вкладке и положение ссылки на странице. Перед публикацией проверяется документ по выбранному URL: локальный файл или внешний PDF без авторизации. До получения необходимых материалов допустим локальный черновик с явными отметками; публичный релиз с заглушками запрещён.

### Заголовок и анимация

Имя «Максим Коляченко» и роль «Fullstack-разработчик» постоянны. Заголовок состоит из «Я» и сменяемой части. Предусмотрены предоставленные автором фразы: «Сделал этот сайт за выходные», «лучший разработчик Сбера 2023», «люблю вайбкодить», «круто презентую идеи», «хочу работать в R&D».

Фраза «Сделал этот сайт за выходные» включена по запросу автора для оценки оформления карусели; перед публичным релизом проверить фактический срок. Имя исключено из карусели, поскольку уже показано над ней. Текст о деплое и CI/CD также описывает проверенный результат. Фразы и их доступность хранятся в данных, без переписывания компонента.

Проектный интервал автосмены — 6 секунд, переход — короткое исчезновение и появление. Есть только кнопки предыдущей/следующей фразы, без отдельной паузы или запуска. Наведение на переключатель или фокус внутри него приостанавливают автосмену. Если ручного перехода не было, после ухода и указателя, и фокуса начинается новый интервал 6 секунд.

После ручного перехода отсчитываются 30 секунд бездействия; новое ручное действие с переключателем сбрасывает этот отсчёт. По истечении ожидания при отсутствии наведения и фокуса показывается следующая фраза, затем действует обычный интервал 6 секунд. Если ожидание истекло при наведении или фокусе, автосмена возобновляется после устранения обеих причин остановки. Выход указателя не снимает остановку, пока фокус остаётся внутри. Действия в других разделах страницы не сбрасывают этот локальный отсчёт.

При `prefers-reduced-motion` автосмена и автоматическое возобновление выключены, ручная смена мгновенная. Фокус не переносится, автоматические смены не создают непрерывных объявлений для скринридера. Высота блока учитывает самую длинную фразу на каждом размере экрана.

### Визуальная композиция

На широком экране портрет и знакомство располагаются рядом, ниже — компактная сетка кейсов. На узком экране — последовательная колонка, переносы длинных фраз и доступные без горизонтальной прокрутки ссылки. Проверочные ширины: 360, 768 и 1440 CSS-пикселей, дополнительно масштаб текста 200%. Проверяется контраст текста и фокуса. Декоративные элементы не перехватывают ввод и не добавляют бессодержательных объявлений.

Портрет используется отдельным локальным ресурсом с осмысленным альтернативным текстом; изображения готовятся заранее в подходящих размерах. Серверная оптимизация `next/image` в статическом экспорте не предполагается: допустимы обычный `img`/`picture` либо совместимый режим без серверного оптимизатора. Шрифты размещаются локально или используются системные, чтобы чтение не зависело от внешних сервисов.

### Доставка и проверки

CI на открытых pull request, push в `main` и `develop`, а также после merge PR в `production` выполняет чистую установку, lint, проверку форматирования, проверку типов и production-сборку. Нужен небольшой smoke-набор для пользовательских сценариев: порядок кейсов и ссылки резюме, ручная смена фраз/пауза, получение контактов из фиктивной runtime-конфигурации и обработка её недоступности. Для визуальной части достаточно ручной проверки ключевых ширин и клавиатуры; снимочные тесты CSS не планируются.

Деплой запускается по `push` в `production` после проверки через GitHub API: SHA должен совпадать с итоговым коммитом слитого PR в `production` из разрешённой ветки. Затем этот SHA повторно собирается и проверяется. Допускаются только исходная ветка `develop` либо непустые имена с префиксами `release/` и `hotfix/`; отдельный check `production-source` проверяет исходную ветку PR и происхождение SHA при push в production до сборки. Прямой push и закрытие PR без merge не публикуют сайт. В GitHub для `production` требуется защита: изменения только через PR, обязательные checks `production-source` и `verify`, актуальность относительно целевой ветки, запрет force push и удаления, применение к администраторам без обходов. Workflow сам по себе не запрещает merge: до включения защиты ограничение в GitHub не считается действующим. Environment `production` допускает доставку только из ветки `production`. Серверные параметры и SSH-ключ передаются через GitHub Secrets. Проверка host key включена, доставка выполняется отдельным пользователем в каталог только этого сайта. Очередь GitHub Actions дополняется серверной блокировкой и защитой от устаревших запусков; формат workflow сверяется с [документацией GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

Сборка загружается в отдельный каталог релиза и проходит preflight до переключения. Детали интеграции, публикации и отката приведены ниже. HTML требует повторной проверки актуальности кеша, хешированные ресурсы кешируются надолго; для JSON и PDF действует `no-store`. Сжатие и размеры изображений проверяются на собранной странице.

### Интеграция с Docker-gateway

Выбран отдельный Compose-проект `/opt/kolyach-dev` с nginx-контейнером, `restart: unless-stopped`, внешней сетью `web` и уникальным alias `kolyach-dev`. Порты хоста не публикуются. Проверенный образ nginx фиксируется digest при реализации. Внутренний nginx обслуживает только HTTP; TLS и ACME остаются на существующем gateway. Постоянный Next.js-процесс не запускается.

В `/opt/web-gateway/nginx/conf.d/dev.kolyach.me.conf` добавляется один virtual host. Как в существующем runbook gateway, upstream задаётся переменной `http://kolyach-dev:80` с `resolver 127.0.0.11`, чтобы смена IP контейнера не требовала reload. После успешного `nginx -t` выполняется graceful reload работающего gateway; его Compose и соседние маршруты не меняются. HTTP сохраняет ACME webroot, остальные запросы после выпуска сертификата перенаправляются на HTTPS. Новый сертификат выпускается существующим Certbot и включается в ежедневное продление.

Альтернатива — раздавать файлы прямо из gateway — потребовала бы новых mounts и пересоздания общей точки входа. Самостоятельный nginx на хосте конфликтует с занятыми портами 80/443. Отдельный контейнер соответствует существующей архитектуре и отделяет жизненный цикл сайта от других проектов.

### Каталоги и mounts

```text
/opt/kolyach-dev/                       # Compose и конфигурация внутреннего nginx
/srv/kolyach-dev/
  releases/<release-id>/                # Проверенный out/ из CI
  live/current -> ../releases/<id>      # Указатель версии
  assets/_next/static/                 # Общие хешированные ресурсы
  shared/runtime-config.json           # Публичная конфигурация
  shared/resume.pdf                    # Только локальный вариант PDF
  tools/                               # Серверные скрипты и валидатор
```

Контейнер получает только `releases`, `live`, `assets` и `shared`, каждый через read-only bind mount по тому же абсолютному пути. Корень nginx — `/srv/kolyach-dev/live/current`. Монтируется каталог `live`, а не разрешённый путь самого symlink; для JSON и PDF также монтируется родительский `shared`, а не отдельные файлы. Поэтому атомарное переименование на хосте видно в уже работающем контейнере. Tools, env, служебные данные публикации и приватные ключи в mounts не входят. Нет HTTP-маршрута для произвольного чтения каталогов сервера.

Это меняет текущую реализацию: указатель переносится из `current` в `live/current`, внутренний конфиг отделяется от TLS-конфига gateway. Публичная конфигурация содержит только разрешённые поля JSON; исходный env — вне публичного дерева с правами 600.

### Среда и разделение доступа

Администратор однократно устанавливает Node.js 24 в `/opt/node24`, серверные команды и workflow используют `/opt/node24/bin/node`. Сохраняются `generate-runtime.mjs`, `activate-release.mjs` и общий TypeScript-валидатор. На VPS не устанавливаются npm-зависимости и не собирается Next.js. Альтернатива с краткоживущим Node-контейнером потребовала бы административного wrapper; CI не получает Docker-доступ ради активации.

Для CI создаётся отдельный SSH-пользователь без sudo и групп `docker` и `web`. Он пишет только релизы, `assets`, `live` и необходимые служебные данные публикации вне mounts; не изменяет tools, runtime Node.js, shared, env, конфиги gateway или TLS. Runtime JSON и локальный PDF доступны ему для чтения preflight, nginx — для раздачи. Env и постоянные файлы обновляет автор, Node.js и tools — администратор. Используется отдельный SSH-ключ CI, а не личный ключ PuTTY. Текущий доступ позволяет обследование через Docker; административные изменения ещё не выполнены, passwordless sudo недоступен.

### Активация, ресурсы и откат

Активация и явный откат используют общую серверную блокировку, удерживаемую до проверки результата и возможного возврата. Под блокировкой активатор проверяет порядок запусков CI и отклоняет запуск старее уже успешно опубликованного. Служебные данные хранят идентификатор запуска и попытки, SHA и предыдущий релиз; факт более нового успешного запуска сохраняется при ручном откате. Повтор того же запуска обрабатывается без повторного переключения уже опубликованного релиза. Явный откат отделён от обычного CI-деплоя и может выбрать более старую сохранённую версию.

До переключения проверяются пути внутри `releases`, HTML, портрет, ссылки на ресурсы сборки, JSON, выбранный локальный PDF либо внешний HTTPS-PDF без авторизации и доступность файлов с реальными правами контейнера. На первом запуске, до старта контейнера, выполняется файловый preflight; до подключения публичного маршрута обязательно проверяется чтение и HTTP-раздача из сети `web`. Неуспешные проверки оставляют прежнюю версию.

Новые хешированные ресурсы добавляются в общий `assets/_next/static` до переключения. Существующий путь с другим содержимым отклоняется. Внутренний nginx раздаёт `/_next/static/` из этого каталога, независимо от `live/current`: открытая старая страница сохраняет доступ к своим JS/CSS после деплоя и отката. На первом этапе автоматического удаления assets нет; отдельная ручная очистка должна учитывать сохраняемые релизы, кеширование и срок поддержки старых страниц.

После атомарного переключения `live/current` проверяются HTTPS-страница, соответствие опубликованному SHA и ресурсы. При ошибке под той же блокировкой восстанавливается предыдущий указатель, результат возврата проверяется и деплой отмечается неуспешным. Если возврат тоже неуспешен, это явно фиксируется как требующее вмешательства, без ложного успешного статуса. Первый релиз без предшественника возвращается к состоянию без нового virtual host по административной процедуре; CI не получает права изменять gateway для этого случая.

При обычной доставке контейнер и gateway не перезапускаются. Очистка сохраняет последние пять успешных релизов и текущий релиз даже после отката; выполняется под общей блокировкой после проверки реальных абсолютных путей. Shared, tools, env и соседние проекты не затрагиваются; глобальный Docker prune запрещён. Ограничение числа каталогов релизов не является разрешением удалить assets старых страниц.

## Risks / Trade-offs

- Недостающие документ по выбранному URL, портрет, телефон, Telegram и URL исходников → получить материалы отдельными короткими задачами; не заменять их выдуманными данными.
- Общий gateway обслуживает несколько проектов → добавлять только новый virtual host, делать резервные копии вне `conf.d`, проверять nginx до reload и сравнивать соседние сайты с исходным состоянием.
- Ограниченный диск и память → сборка только в CI, последние пять успешных релизов плюс текущий; assets контролируются отдельно, без глобального prune.
- Bind mount самого symlink или файла скрывает атомарную замену → монтировать родительские каталоги и проверять переключение при работающем контейнере.
- Запоздавший CI или конкурирующий откат → общая блокировка, проверка порядка публикаций и сохранение отметки последнего успешного запуска при откате.
- На VPS нет Node.js 24, GitHub CLI ранее вернул 401 → установка среды администратором и отдельная проверка доступа к GitHub перед настройкой Secrets и защиты ветки.
- 2popuga.kolyach.me уже возвращал 502 при обследовании → учитывать исходный сбой отдельно; исправление этого проекта не входит в интеграцию.
- Срок «за выходные» может не совпасть с реальностью → подтвердить фразу перед релизом или исключить её из публичного набора.
- Метрики опыта изменяются → считать числа снимком со слов автора при подготовке сайта, повторно сверить перед релизом; сумму сделок не называть выручкой, созданной CRM.
- Растровый макет перегружает узкий экран → отдельная мобильная композиция и упрощение декора; читаемость важнее точного совпадения каждого свечения.
- Статическая публикация требует пересборки для обновления текста страницы → это приемлемо для MVP и автоматизируется CI/CD; PDF обновляется независимо, динамические функции станут отдельным изменением.

## Migration Plan

1. Подготовить Compose, внутренний nginx, отдельный конфиг gateway, обновлённый активатор и документацию. Локально проверить реальные mounts, переключение symlink, атомарную замену JSON/PDF, старые JS/CSS, гонки и возврат после ошибки публикации.
2. Администратором создать `/opt/kolyach-dev`, `/srv/kolyach-dev`, отдельного CI-пользователя и Node.js 24, установить tools и права. Автор задаёт env и выбранное резюме вне публичных каталогов и git.
3. Передать проверенную сборку, выполнить файловый preflight, запустить только новый контейнер и проверить раздачу из сети `web`, включая права и закрытость служебных файлов.
4. Снять исходные ответы соседних сайтов и резервную копию конфигов gateway вне `conf.d`. Добавить HTTP virtual host с ACME webroot; выполнить `nginx -t`, затем reload без пересоздания gateway.
5. Существующим Certbot выпустить сертификат только для dev.kolyach.me. Добавить HTTPS-конфиг, снова проверить и перечитать nginx. Проверить новый сертификат и участие в текущем продлении; при ошибке остановиться без reload некорректного конфига.
6. Проверить сайт снаружи, выбранный PDF, контакты, интерфейс и соседние сайты. Для первой публикации заранее подготовить административное отключение только нового virtual host при отсутствии предыдущего релиза.
7. Настроить Secrets, environment и защиту `production`. Выполнить следующую доставку через разрешённый PR, проверить postflight и откат. Независимо заменить PDF/JSON и подтвердить их сохранность после деплоя, очистки и отката, а также доступность JS предыдущей страницы.
