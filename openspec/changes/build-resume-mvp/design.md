# Design

## Context

Мотивация и объём описаны в `proposal.md`. В репозитории пока нет приложения: есть npm-проект, локальный OpenSpec 2.0.0, TypeScript и настроенные ESLint/Prettier. Существующих спецификаций нет. Пользователь выбрал Next.js, Ubuntu VPS, nginx и GitHub Actions; Python отложен до отдельной итерации.

Тексты кейсов получены в обсуждении. Документ резюме автор дополняет. Предварительный макет передан изображением: крупная фотография слева, заголовок справа, тёмная основа, тёплые акценты, диагонали и декоративное окно кода. Макет задаёт направление, но не содержит блока кейсов и мобильной композиции. Исходная фотография пока не передана отдельно.

## Goals / Non-Goals

**Goals:**

- Собрать первый пригодный для отправки релиз в пределах 48 часов разработки; получение материалов и доступа к серверу может влиять на календарную дату публикации.
- Сохранить возможность менять тексты и контакты без переработки компонентов, а PDF — непосредственно на сервере без пересборки и деплоя сайта.
- Оставить на сервере простую статическую публикацию и сохранить читаемый контент при недоступности клиентского JavaScript.

**Non-Goals:**

- Проектировать будущий Python API до появления полезного сценария.
- Создавать универсальную систему портфолио, редактор контента или инфраструктуру для других сайтов kolyach.me.
- Копировать растровый макет целиком как интерфейс; тексты, ссылки и кнопки должны быть настоящими элементами страницы.

## Decisions

### Статическая сборка Next.js

Предлагаем App Router, TypeScript и `output: 'export'`: сборка формирует каталог `out`, который отдаёт nginx. Интерактивность сосредоточена в небольшом клиентском компоненте смены фраз. Остальной контент формируется при сборке. Источник: [официальная документация Next.js](https://nextjs.org/docs/app/guides/static-exports).

Версии Next.js, React и поддерживаемого Node.js выбираются совместимыми стабильными на старте реализации и фиксируются lock-файлом и указанием среды Node.js; необоснованные номера сейчас не задаём. Используем имеющиеся npm и конфигурацию `@kolyach/eslint-config`, уже созданную командой `npx @kolyach/eslint-config init`; повторная инициализация не является отдельной задачей.

Альтернативы: постоянный процесс Next.js потребовал бы сопровождения сервиса без полезных серверных функций; Python для раздачи HTML добавил бы аналогичную нагрузку. Чистый HTML мог бы решить задачу, но не соответствует выбранному пользователем Next.js.

### Структура и данные

Одна главная страница: знакомство → четыре кейса → резюме и контакты → рассказ о создании сайта и исходники. В первом экране нет ссылки, позволяющей перейти к резюме до кейсов. Визуальный порядок, порядок DOM и клавиатурного обхода согласованы; прокрутка и доступ к ссылкам не блокируются искусственно.

Предлагаемое размещение при реализации: `src/app/` для страницы и метаданных, `src/components/` для блоков, `src/content/` для типизированных данных, `public/` для портрета и других ресурсов сборки. PDF хранится отдельно на сервере и не включается в `public/`, `out`, git или артефакт доставки. Это будущие файлы, в рамках планирования они не создаются. Снимки проектов необязательны для первого релиза. Декор выполняется преимущественно CSS; библиотека анимаций и внешний UI-kit не нужны для простого переключения.

### Контакты и ссылка на резюме из окружения сервера

Телефон и Telegram задаются на VPS через `CONTACT_PHONE` и `CONTACT_TELEGRAM_URL`. Реальные значения не хранятся в исходниках, git, тестовых данных, логах CI или артефакте сборки. В репозитории документируются только имена переменных и фиктивные примеры. Файл окружения, если он используется, размещается вне публично раздаваемых каталогов.

Дополнительная переменная `RESUME_URL` задаёт адрес PDF-резюме. Если она отсутствует или пуста, используется `/resume.pdf`; также допустим абсолютный HTTPS-адрес. Явно заданный некорректный адрес не заменяется молча значением по умолчанию: генератор сообщает об ошибке и сохраняет прежнюю конфигурацию. При внешнем адресе локальный PDF не требуется для публикации; проверяется доступность документа без авторизации по выбранной ссылке. Условия кеширования внешнего сервиса не контролируются нашим nginx.

Поскольку сайт экспортируется статически, серверные переменные нельзя читать через клиентский `process.env`: значения `NEXT_PUBLIC_*` фиксируются при сборке. Основание: [документация Next.js](https://nextjs.org/docs/app/guides/environment-variables#bundling-environment-variables-for-the-browser). Вместо этого отдельный скрипт на VPS читает только три перечисленные переменные, проверяет телефон и URL, сериализует поля `phone`, `telegramUrl` и `resumeUrl` в JSON и атомарно заменяет файл в постоянном каталоге вне релизов. Весь набор переменных окружения никогда не экспортируется.

nginx отдаёт этот файл по `/runtime-config.json` с типом `application/json` и политикой `Cache-Control: no-store`; кеш открытых файлов для этого адреса отключён. Браузер загружает конфигурацию при открытии страницы, проверяет значения и формирует `tel:`, ссылку Telegram и ссылку резюме. В публичном JSON находятся только предназначенные посетителям поля. Постоянно работающий API или Python-сервис не нужен.

До загрузки, при ошибке сети или неверной конфигурации ссылки резюме и контактов не активируются и не подменяются фиктивными адресами. Посетителю доступно краткое сообщение об их недоступности; детали серверной настройки в интерфейс не выводятся. Без JavaScript показывается сообщение о необходимости JavaScript для контактов и резюме; имя, кейсы и ссылки на исходники и SberUnity доступны как обычный HTML.

Для обновления контактов или ссылки резюме автор меняет окружение и повторно запускает скрипт генерации, без пересборки сайта. Если проверка или генерация завершается ошибкой, прежний JSON сохраняется. Деплой, откат и очистка релизов не заменяют и не удаляют файл окружения и текущую конфигурацию. CI использует только фиктивную конфигурацию для проверки обоих вариантов резюме, успешной загрузки и обработки ошибок; настоящая конфигурация проверяется на VPS перед публикацией.

### Независимое обновление PDF

Ссылка «моё резюме» использует `resumeUrl` из runtime-конфигурации и открывает документ в новой вкладке через `target="_blank"` с `rel="noopener"`. Исходная вкладка сохраняет страницу сайта и положение прокрутки. Ссылка не инициирует принудительное скачивание. Описанные ниже хранение, замена и кеширование локального PDF применяются только при `resumeUrl = /resume.pdf`; внешний вариант не требует файла на VPS.

Полное резюме доступно по постоянному адресу `/resume.pdf`. nginx сопоставляет этот адрес с файлом в постоянном каталоге вне дерева релизов, например `<каталог-сайта>/shared/resume.pdf`. Путь уточняется при настройке VPS и не зависит от указателя текущего релиза. Способ сопоставления описан в [документации nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#alias).

Автор загружает подготовленный PDF через SSH/SFTP под временным именем в том же каталоге, проверяет файл и права чтения nginx, затем атомарно переименовывает его в `resume.pdf`. До успешной замены доступна предыдущая целая редакция; после замены новые запросы получают новую. Пересборка, коммит, GitHub Actions и перезапуск или перезагрузка nginx для обычной замены файла не нужны. Веб-интерфейс загрузки не создаётся.

Для этого адреса задаётся `Content-Type: application/pdf` и политика `Cache-Control: no-store`; отключаются унаследованный кеш открытых файлов и условные ответы, способные вернуть старую редакцию при совпадении размера и времени изменения. Проверяется повторный запрос по тому же URL после замены, в том числе при одинаковом размере файлов. Заголовки настраиваются средствами [nginx](https://nginx.org/en/docs/http/ngx_http_headers_module.html#add_header). Уже открытая вкладка PDF сама не обновляется: гарантия относится к следующему открытию/запросу.

Сборка и CI не требуют наличия реального резюме. Smoke-проверки используют фиктивные `/resume.pdf` и внешний HTTPS-адрес, проверяют открытие в новой вкладке и положение ссылки на странице. Перед публикацией проверяется документ по выбранному URL: локальный файл или внешний PDF без авторизации. До получения необходимых материалов допустим локальный черновик с явными отметками; публичный релиз с заглушками запрещён.

### Заголовок и анимация

Имя «Максим Коляченко» и роль «Fullstack-разработчик» постоянны. Заголовок состоит из «Я» и сменяемой части. Предусмотрены предоставленные автором фразы: «Сделал этот сайт за выходные», «лучший разработчик Сбера 2023», «люблю вайбкодить», «круто презентую идеи», «хочу работать в R&D».

Фраза «Сделал этот сайт за выходные» включена по запросу автора для оценки оформления карусели; перед публичным релизом проверить фактический срок. Имя исключено из карусели, поскольку уже показано над ней. Текст о деплое и CI/CD также описывает проверенный результат. Фразы и их доступность хранятся в данных, без переписывания компонента.

Проектный интервал автосмены — 6 секунд, переход — короткое исчезновение и появление. Есть только кнопки предыдущей/следующей фразы, без отдельной паузы или запуска. Наведение на переключатель или фокус внутри него приостанавливают автосмену. Если ручного перехода не было, после ухода и указателя, и фокуса начинается новый интервал 6 секунд.

После ручного перехода отсчитываются 30 секунд бездействия; новое ручное действие с переключателем сбрасывает этот отсчёт. По истечении ожидания при отсутствии наведения и фокуса показывается следующая фраза, затем действует обычный интервал 6 секунд. Если ожидание истекло при наведении или фокусе, автосмена возобновляется после устранения обеих причин остановки. Выход указателя не снимает остановку, пока фокус остаётся внутри. Действия в других разделах страницы не сбрасывают этот локальный отсчёт.

При `prefers-reduced-motion` автосмена и автоматическое возобновление выключены, ручная смена мгновенная. Фокус не переносится, автоматические смены не создают непрерывных объявлений для скринридера. Высота блока учитывает самую длинную фразу на каждом размере экрана.

### Визуальная композиция

На широком экране портрет и знакомство располагаются рядом, ниже — компактная сетка кейсов. На узком экране — последовательная колонка, переносы длинных фраз и доступные без горизонтальной прокрутки ссылки. Проверочные ширины: 360, 768 и 1440 CSS-пикселей, дополнительно масштаб текста 200%. Проверяется контраст текста и фокуса. Декоративные элементы не перехватывают ввод и не добавляют бессодержательных объявлений.

Портрет используется отдельным локальным ресурсом с осмысленным альтернативным текстом; изображения готовятся заранее в подходящих размерах. Серверная оптимизация `next/image` в статическом экспорте не предполагается: допустимы обычный `img`/`picture` либо совместимый режим без серверного оптимизатора. Шрифты размещаются локально или используются системные, чтобы чтение не зависело от внешних сервисов.

### Доставка и проверки

CI на pull request выполняет чистую установку, lint, проверку форматирования, проверку типов и production-сборку. Нужен небольшой smoke-набор для пользовательских сценариев: порядок кейсов и ссылки резюме, ручная смена фраз/пауза, получение контактов из фиктивной runtime-конфигурации и обработка её недоступности. Для визуальной части достаточно ручной проверки ключевых ширин и клавиатуры; снимочные тесты CSS не планируются.

После успешных проверок push в выбранную основную ветку запускает автоматический деплой. Ветка определяется по фактическому репозиторию при реализации. Серверные параметры и SSH-ключ передаются через GitHub Secrets. Проверка host key включена, доставка выполняется отдельным пользователем в каталог только этого сайта. Последовательная публикация релизов исключает гонку обновлений; формат workflow сверяется с [документацией GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

Сборка загружается в отдельный каталог релиза, проверяются главная страница, ресурсы и доступность документа по выбранному resumeUrl, затем переключается указатель текущего релиза. Доставка и очистка старых релизов не изменяют постоянный каталог PDF. nginx отдаёт сайт по HTTPS и перенаправляет HTTP. Предыдущая версия страницы и её ресурсов сохраняется для отката; откат сайта сохраняет текущую редакцию PDF. HTML требует повторной проверки актуальности кеша, хешированные ресурсы могут кешироваться надолго; для PDF действует отдельная политика выше. Сжатие и размеры изображений проверяются на собранной странице. Контейнеры для статического сайта в первом релизе не нужны.

## Risks / Trade-offs

- Недостающие документ по выбранному URL, портрет, телефон, Telegram и URL исходников → получить материалы отдельными короткими задачами; не заменять их выдуманными данными.
- Домен предварительный, доступ к VPS и состояние nginx неизвестны → подтвердить параметры перед публикацией, подготовить выделенный virtual host, проверить другие сайты после изменения.
- Срок «за выходные» может не совпасть с реальностью → подтвердить фразу перед релизом или исключить её из публичного набора.
- Метрики опыта изменяются → считать числа снимком со слов автора при подготовке сайта, повторно сверить перед релизом; сумму сделок не называть выручкой, созданной CRM.
- Растровый макет перегружает узкий экран → отдельная мобильная композиция и упрощение декора; читаемость важнее точного совпадения каждого свечения.
- Статическая публикация требует пересборки для обновления текста страницы → это приемлемо для MVP и автоматизируется CI/CD; PDF обновляется независимо, динамические функции станут отдельным изменением.

## Migration Plan

1. Получить публичные материалы и параметры публикации; зафиксировать совместимые версии среды.
2. Собрать страницу, локальные ресурсы, проверки и production-экспорт.
3. Подготовить выделенный каталог сайта, nginx, DNS и HTTPS. При локальном варианте подготовить постоянный каталог PDF и загрузить документ; при внешнем — проверить HTTPS-ссылку без авторизации. Не изменять конфигурации соседних сайтов.
   Задать контактные переменные и при необходимости RESUME_URL на VPS и сформировать первую runtime-конфигурацию вне каталогов релизов.
4. Опубликовать первую проверенную сборку, проверить URL, PDF, контакты и поведение интерфейса.
5. Проверить изменение RESUME_URL без пересборки; для локального варианта также заменить PDF и проверить новую редакцию по прежнему URL. Проверить автоматическую доставку следующей версии сайта и возврат на предыдущий релиз: оба действия сохраняют обновлённый PDF. Для первой публикации без предшественника возврат означает отключение только нового virtual host, без удаления постоянного документа.

## Open Questions

- Финальные значения телефона, Telegram, URL GitHub, выбранный домен и путь на VPS — параметры, которые можно получить перед соответствующими задачами, не меняя архитектуру.
- Действительный PDF по выбранному локальному или внешнему URL и исходный портрет — материалы автора; без них публичный релиз не считается готовым.
- Год начала эксплуатации mini-CRM автор не указал: сохраняем формулировку «с июня» до уточнения и не дописываем год автоматически.

### Уточнения оформления

У разделов указаны номера: «01 / Знакомство», «02 / От замысла к результату», «03 / Продолжим знакомство», «04 / Этот сайт — тоже мой проект». У резюме вместо стрелки используется иконка PDF, у действий связи — иконки телефона и Telegram. SVG декоративные, доступные названия ссылок определяются их текстом.
